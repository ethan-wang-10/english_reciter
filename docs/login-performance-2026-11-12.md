# 登录加载性能排查（2026-11-12）

`ethan` 的历史慢请求中，首屏 `/api/bootstrap` 有 22 条记录，中位耗时
2087 ms、最长 12826 ms；后台 `/api/challenges` 有 64 条记录，中位耗时
4364 ms。日志包含慢请求和少量普通请求抽样，这些数字不代表全部请求的分布。

线上已经使用 `include_gamification=0`，因此将奖励数据移出首屏的旧优化已经生效。
本次瓶颈来自后台 PK 列表：33 条记录中有 15 场已经结算的 PK，每次轮询仍重新
读取双方完整的奖励历史来统计打卡，合计加载 30 次，其中 `ethan` 加载 15 次。
JSON 解析、账本校验和练习事件归一化产生大量重复 CPU 工作。

生产服务运行一个 Gunicorn worker、四个线程。隔离副本复现表明，挑战请求的
CPU 工作会明显拖慢同一进程内并发的首屏请求；不是密码验证在加载学习历史。

修复后，已结算的 PK 直接使用结算时保存的 `days_a` / `days_b`，分数与发奖依据
保持一致。未结算或缺少历史分数的旧记录仍按原计分区间计算，但同一次列表请求
对每位参与者只加载一次奖励状态。缓存仅存在于该次调用，下一次轮询会读取新的
真实打卡记录；补签仍不计入 PK。

| 同服务器隔离副本实测 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 挑战列表，不启用 profiler | 3856 ms | 4–5 ms |
| 一次挑战列表加载奖励状态次数 | 30 | 0 |
| 首屏首次加载，无并发挑战 | 663 ms | 674 ms |
| 首屏，同时发起两条挑战请求 | 4453 ms | 421 ms |

数据来自 SQLite 只读连接的 `backup()` 副本；代码、词库和用户状态均在独立目录
运行，Flask 使用 testing 模式，并关闭后台任务。计时是本次对照实验的样本，
不包含浏览器渲染、网络传输和代理排队。修改后连续五次挑战查询为
4.50 / 4.32 / 4.30 / 4.29 / 4.26 ms，且 33 条完整返回结果与修改前逐条相等。

新增回归覆盖：大量已结算历史、进行中 PK 的参与者复用与下一次轮询更新、
旧记录缺失分数、跨月结算与发奖幂等，以及无计分区间时避免加载账户。
同时运行既有挑战、奖励存储、游戏化、XP 修正和首屏接口相关测试，共 95 项通过。
